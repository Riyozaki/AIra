## 1. Нотация

N — число параметров (N_ne без эмбеддингов); L — слои; d — ширина; V — словарь; T — длина контекста; D — число токенов обучения; B — батч (последовательностей); b_w, b_kv — байт на вес или элемент KV; P — пиковая производительность (FLOP/s); β — пропускная способность памяти (байт/с); u — утилизация (MFU); e_op, e_mem — энергия на операцию или байт.

## 2. FLOPs и параметры

```
N_ne      = 12·L·d²                                   (attn 4d² + MLP 8d²)
F_fwd(T)  = 2·N_ne + 2·V·d + 2·L·T·d                  FLOP на токен
C_train   = 3 · F_fwd · D  ≈ 6·N·D + 6·L·T·d·D        (fwd + bwd, bwd ≈ 2·fwd)
attn_frac = T / (12·d + T + V/L)
```

**Следствие 2.1 (оценка).** При T = 2048 доля внимания составляет 13.3% (124M), 7.1% (1.3B), 3.9% (7B), 2.3% (~57B) (таблица A). Замена внимания на что угодно ускоряет обучение на коротком контексте **не более чем в 1/(1 − attn_frac) = 1.02–1.15 раза**. Внимание доминирует только при T ≳ 12d (для 7B это T ≳ 50k).

## 3. Обучение: вычисления, память, время, энергия

```
Память состояния   M_state = N·(2 bf16 веса + 2 bf16 град. + 4 fp32 master + 4 m + 4 v) = 16·N байт
Память активаций   M_act   = B·T·d·L·(34 + 5·a·T/d)   байт   (без recompute)
Время              t       = C_train / (P·u)
Энергия (board)    E       ≈ t · W_TDP · PUE
Энергия (на опер.) E       ≈ C_train · e_flop + Q_dram · e_dram
```

**Таблица A (оценка, `results/cost_model_tables.md`):**

|---|---|---|---|---|---|---|---|
| GPT-2 small | 124M | 2.5B | 2.1e18 | ≈1.5 | ≈1 | 2.0 | 2.2 |
| ~1.3B | 1.31B | 26B | 2.2e20 | 156 | 131 | 21 | 11.5 |
| ~7B | 6.7B | 134B | 5.5e21 | 3 865 | 3 247 | 107 | 30.6 |
| ~57B | 57B | 1.1T | 3.9e23 | 276 390 | 232 168 | 914 | 153 |

**Где теряются ресурсы при обучении:**
- **Память.** У 7B веса bf16 занимают 13.4 ГБ, а полное состояние обучения — 107 ГБ плюс активации. Значит, **≈88–90% памяти обучения — не веса**: это градиенты, fp32-копия и моменты Adam (12 из 16 байт на параметр приходятся на оптимизатор), плюс активации для backprop.
- **Вычисления.** 2/3 FLOPs уходят на обратный проход, при MFU 40% простаивает 60% пиковой производительности. Каждый токен получает полные 2N FLOPs независимо от сложности.

## 4. Инференс: prefill против декодирования

```
Prefill (на T токенов): FLOPs = T·F_fwd,  байты ≈ N·b_w        → compute-bound
Декодирование (B посл., 1 шаг):
   FLOPs  = B·F_fwd(T)
   байты  = N·b_w + B·T·(2·L·d·kv_ratio·b_kv)                  (веса + KV-кэш)
   t_step ≥ max(FLOPs / P,  байты / β)                          (roofline)
   арифметическая интенсивность I = FLOPs / байты ≈ 2B/b_w  (пока KV мал)
   ridge point  I* = P / β       (H100: 295 FLOP/байт; T4: 203; песочница fp32: ≈10)
```

**Таблица B (оценка, декодирование при batch = 1, T = 4096):**

| Модель | Железо | Нижняя граница, мс/токен | Утилизация вычислений |
|---|---|---|---|
| 124M | H100 | 0.12 | **0.27%** |
| 7B | H100 | 4.6 | **0.31%** |
| 7B | T4 | 48.6 | 0.45% |
| 124M | песочница (fp32) | 34.6 | 3.9% |

| B | I, FLOP/байт | утилизация | KV, ГБ |
|---|---|---|---|
| 1 | 0.9 | 0.3% | 2.1 |
| 32 | 5.5 | 1.9% | 69 |
| 512 | 6.5 | 2.2% | 1 100 (не помещается) |

**Где теряется 99%.** При декодировании **99.7% вычислительной мощности GPU простаивает** (оценка по roofline). Время определяется только объёмом байт, прочитанных на токен.

**Нижняя граница 4.1 (строгая, следует из roofline).** Без кэширования весов на кристалле каждый вес нужно прочитать хотя бы раз на шаг. Отсюда:
```
t_token ≥ (байт весов, не помещающихся в быструю память + байт KV) / β
```
Ускорить декодирование при batch = 1 в k раз можно только тремя путями:
1. уменьшить число **читаемых** байт на токен в k раз (битность, разреженное или условное чтение);
2. перенести веса в память с β в k раз выше (SRAM/кэш);
3. получать k токенов на одно чтение весов (multi-token или спекулятивное декодирование).

Других путей нет.

## 5. Энергия

Таблица Horowitz (ISSCC 2014, 45 нм; по [mlsysbook](https://mlsysbook.ai/vol1/backmatter/appendix_assumptions.html) и [safeguard.sh](https://safeguard.sh/resources/blog/cpu-vs-gpu-vs-qpu-explained-how-each-processor-works-what-each-is-good-at-and-why-they-coexist)):

| Операция | pJ |
|---|---|
| INT8 add | 0.03 **[НП]** |
| INT8 mult | 0.2 |
| FP16 mult | 1.1 |
| FP32 add / mult | 0.9 / 3.7 |
| SRAM (кэш) чтение | 10–100 (в зависимости от размера) |
| DRAM, 32 бита | 640 (≈160 pJ/байт) |

**Оценка 5.1 (декодирование 7B, bf16, batch = 1, константы 45 нм / DDR).**
- Память: 13.4 ГБ × 160 pJ/байт ≈ **2.1 Дж/токен**.
- Арифметика: 13.4 GFLOP × ~1.5 pJ ≈ **0.02 Дж/токен**.
- Итого **≈99% энергии декодирования — перемещение данных**. С HBM на современном узле абсолютные числа меньше, но порядок соотношения тот же (допущение A9).

**Оценка 5.2 (обучение).** Обучение compute-bound: GEMM с M = B·T ≈ 10⁶ токенов на шаг имеет высокую интенсивность. На уровне платы H100 700 Вт / 989 TFLOP/s ≈ 0.71 pJ/FLOP при 100% загрузке и ≈1.8 pJ на **полезный** FLOP при MFU 40%.

Отсюда энергия обучения ≈ FLOPs / u × e_flop. Рычаги:
- меньше FLOPs;
- выше u;
- дешевле операция. INT8 mult дешевле FP32 mult в ~18 раз; тернарное умножение вырождается в сложение (INT8 add 0.03 pJ), но **это энергия схемы**, а не реальная экономия на GPU общего назначения.

## 6. Где теряются 90–99% ресурсов: декомпозиция

Ниже «потеря» означает разницу между тем, что тратит базлайн (A1), и тем, что минимально необходимо **по известным данным**. Множители — **оценки**.

| # | Ресурс | Механизм потери | Формула | Доля потерь | Подтверждённое снижение (литература) | Предел |
|---|---|---|---|---|---|---|
| L1 | Вычисления при декодировании | Bandwidth-bound | u = I/I* = (2B/b_w)/I* | **99.7%** при B = 1 на H100 | Батчинг (сервер), меньше b_w, кэш | Нижняя граница 4.1 |
| L2 | Биты весов | bf16 при ёмкости ≈2 бит/параметр | 1 − 2/16 | **87.5%** бит избыточны | Тернарность 1.58 бит: паритет при ≥3B (BitNet) | §7.4: ≈×8–10 по битам |
| L3 | Энергия декодирования | DRAM ≫ ALU | Q·e_dram / (Q·e_dram + W·e_op) | **≈99%** на перемещение | LUT/тернарность: −55–82% (T-MAC, bitnet.cpp) | Байты весов на токен |
| L4 | Память обучения | Состояние Adam + активации | 1 − 2N / (16N + M_act) | **≈88–90%** не веса | 8-битные состояния; без моментов (ES/ZO) | Хотя бы веса + один буфер |
| L5 | Вычисления обучения: простой | MFU < 1 | 1 − u | 54–62% | MFU до 55% (MegaScale) | u → ~0.7–0.8 практически |
| L6 | Вычисления обучения: обратный проход | Цена градиента | 2/3 FLOPs | 67% | Нет метода без потери качества | ≤×3 (§7.2) |
| L7 | Вычисления на токен | Плотность: все токены получают 2N | 1 − 1/EL | ≈86% при EL = 7 | MoE EL ≈ ×7 при 1e22 FLOPs | Растёт с бюджетом; на малом масштабе меньше |
| L8 | Токены | Неэффективность по данным | D_base / D_min | ≈97% против рецепта 2019 г. (×30, speedrun) | Speedrun: 10B → <330M токенов | Неизвестен; §7.5 |
| L9 | Точность арифметики | bf16 там, где хватает 4–8 бит | throughput fp4 / bf16 | 50–75% | NVFP4 ≈ FP8 на 12B/10T; FP8 стандарт | Оптимум ~7–8 бит (Kumar) |
| L10 | Оптимизатор | Скалярная преобусловленность | 1 − 1/s | 10–30% | Muon ×1.1–1.4 | Убывает с масштабом |

**Честный вывод:**
1. Буквально «90–99%» теряется в четырёх местах: **декодирование** (L1, L3), **избыточные биты** (L2), **память обучения** (L4).
2. В **вычислениях обучения** нет ни одного фактора с потерей ≥90%. Потери распределены по L5–L10, и выигрыш получается только **перемножением**:
   ```
   Эффективный запас (оценка) ≈ 1/u-рост (×1.5) · точность (×2) · условные вычисления (×3–7) · оптимизатор (×1.2) · данные (×?)
                              ≈ ×11–25 · (данные)
   ```
   Факторы **не независимы**:
   - MoE снижает MFU (маршрутизация, коммуникации);
   - низкая точность ухудшает «эффективные параметры» (Kumar et al.);
   - эффект данных зависит от модели.
3. Относительно **современного** базлайна (MoE + FP8 + Muon уже в продакшене) оставшийся известный запас заметно меньше. Это нужно признать заранее.

## 7. Нижние границы

### 7.1 Roofline и I/O-сложность
`t ≥ max(W/P, Q/β)`, где W — FLOPs, Q — байты между уровнями памяти. Для умножения матриц n×n с кэшем размера M известна I/O-граница Hong–Kung: Q = Ω(n³/√M) **[НП: классический результат 1981 г., цитирую по памяти]**. Для GEMV (декодирование) Q ≥ размер матрицы, значит, верна граница 4.1. Это **жёсткое** физико-алгоритмическое ограничение: никакая «новая математика» не обходит его без уменьшения Q.

### 7.2 Цена градиента и предел «отказа от backprop»
Обратный режим автодифференцирования: cost(∇f) ≤ ω·cost(f), где ω — небольшая константа (принцип «дешёвого градиента», Baur–Strassen 1983; Griewank–Walther) **[НП: по памяти]**. Для плотных слоёв fwd = 2N, bwd = 4N, шаг стоит 3F.

**Следствие:** любой метод, которому нужен хотя бы один прямой проход на пример, при **том же числе шагов** выигрывает по вычислениям не более ×3. Методы нулевого порядка (SPSA/ES) платят ростом числа шагов. Дисперсия оценки растёт с эффективной размерностью **[НП: Nesterov–Spokoiny 2017, Duchi et al. 2015 — по памяти]**. Эмпирически MeZO делает в 32 раза больше шагов (на дообучении, где эффективный ранг мал); на предобучении с нуля ожидаемо хуже.

**Вывод:** ×10–100 по стоимости обучения из отказа от backprop невыводимы. Отказ от backprop имеет смысл только как средство (недифференцируемые дискретные модели, память), а не как цель.

### 7.3 Эмпирическая граница: законы масштабирования и «множитель эффективных вычислений»
Chinchilla: `L(N,D) = E + A/N^α + B/D^β`, подогнанные значения E ≈ 1.69, A ≈ 406, B ≈ 411, α ≈ 0.34, β ≈ 0.28 **[НП: по памяти из arXiv 2203.15556]**. На compute-optimal траектории `L*(C) − E ∝ C^(−γ)`, где γ = αβ/(α+β) ≈ 0.15.

**Следствия (оценка):**
1. **Как честно измерить «×k».** Подогнать кривую L_base(C) по ≥4 точкам базлайна. Для нашей модели с потерей L_new при затратах C_new найти C_eq = L_base⁻¹(L_new). Множитель эффективных вычислений `ECM = C_eq / C_new`.
2. **Чувствительность.** Множитель ×10 соответствует уменьшению *уменьшаемой* части loss всего в 10^0.15 ≈ 1.41 раза. Обратно: ошибка в loss δ даёт относительную ошибку ECM ≈ δ / (γ·(L − E)). Шум в 1% от уменьшаемой части loss даёт ≈7% ошибки в ECM. Поэтому нужно много seed и доверительные интервалы.
3. Множитель ×10–100 требует изменить **константы** закона (A, B, α, β), то есть архитектуру и эффективность по данным, либо стоимость одного FLOP. Повышение утилизации даёт только константу.

### 7.4 Информационная граница размера модели
По Allen-Zhu & Li (ICLR 2025) ёмкость составляет ≈2 бита знаний на параметр, в том числе в int8.
```
бит хранения ≥ K (бит знаний, которые нужны задаче)
избыточность bf16 = 16 / 2 = 8×;  тернарные 1.58 бит ≈ у потолка
```
**Следствие (оценка):**
- «Бесплатное» сжатие размера ограничено ≈×8–10 и почти исчерпывается тернаризацией.
- Сжатие ×10–100 **при равном качестве на задачах со знаниями** невозможно, если граница 2 бита/параметр верна для нашей архитектуры. Возможно только:
  - (а) на задачах с малым K (алгоритмические, узкие);
  - (б) с выносом знаний во внешнюю или медленную память. Это перенос: читаемые на токен байты уменьшаются, хранимые — нет.
- Нижняя граница loss — энтропия данных E. Её не обходит ни одна архитектура.

### 7.5 Данные
Для запоминания факта нужно ≈100–1000 его повторений: по Allen-Zhu & Li, при ~1000 экспозиций достигается 2 бита/параметр, при ~100 — около 1 бита **[НП: детали по памяти]**. Speedrun показывает, что практические рецепты были далеки от предела (×30 по токенам), но где сам предел для LM, неизвестно. Это **открытый вопрос и главный неопределённый множитель** во всей модели.

### 7.6 Физика энергии
Предел Ландауэра kT·ln2 ≈ 2.9·10⁻²¹ Дж при 300 K. Современные операции стоят ~10⁻¹² Дж, это на 9 порядков выше, так что предел **не ограничивает**. Ограничивает энергия перезарядки проводников: она пропорциональна расстоянию, отсюда DRAM ≫ SRAM ≫ регистр. Практическая нижняя граница:
```
E ≳ Q_offchip · e_dram + Q_onchip · e_sram + W · e_op
```
Решающее значение имеет **Q_offchip**.

### 7.7 Закон Амдала для составных ускорений
`S = 1 / Σ_i (p_i / s_i)`, где p_i — доля затрат компонента, s_i — его ускорение. Примеры (оценка):

| Ускоряемая часть | p | Предел при s → ∞ |
|---|---|---|
| Внимание при T = 2k | 0.04–0.13 | ×1.04–1.15 |
| Обратный проход | 0.67 | ×3 |
| Только матричные умножения (низкая битность), если остальное — 10% времени | 0.9 | ×10 |

Для ×10–100 нужно ускорять **всё**, включая нормализации, элементные операции, ввод-вывод и оптимизатор. Иначе Амдал ограничит выигрыш ×3–10.

| Цель | Формула | Рычаги и ожидаемый множитель (литература) | Реалистичная оценка | Условия |
|---|---|---|---|---|
| **Скорость или стоимость обучения** | Cost = D · c_tok · e_op / u | D: данные (×2–30?); c_tok: условные вычисления и поиск (×3–7); e_op: точность (×2–4 по throughput, ×5–20 по энергии схемы); u: ×1.5 | **×10–30** только при перемножении ≥3 факторов; ×100 требует большого вклада D, а он не доказан | Факторы не должны гасить друг друга |
| **Скорость инференса** (batch = 1, CPU/edge) | t_tok = max(c_tok/P, b_tok/β) | b_tok: биты (×8–10), разреженное чтение (×k), кэш (β ×2.4 **измерено** в песочнице, ×10+ для SRAM), multi-token (×2–3) | **×10–50** | Модель или её «горячая» часть помещается в кэш |
| **Размер модели** | бит = N · b | b: ×8–10 (предел §7.4); N: только для узких задач или с внешней памятью | **×10** реалистично; ×100 только на задачах с малым K | Граница 2 бит/параметр |
| **Энергия** | E ≈ Q·e_mem + W·e_op | Q (биты, кэш) и W·e_op (целые/тернарные операции) | ×10–50 для инференса; для обучения ≈ множитель стоимости | Энергию нельзя измерить в песочнице (нет RAPL) |

**Следствия для фазы 1:**
- Рабочий масштаб — модели на **0.1–5M параметров** и **10–100M токенов** (байтов). На этом масштабе внимание, нормализации и накладные расходы Python занимают намного большую долю, чем в больших моделях, поэтому законы малого масштаба нельзя механически переносить на большой (см. `02_success_criteria.md`, §5).
- Модель ≤ ~40 МБ целиком помещается в L3. Это означает ~200M тернарных параметров или ~10M fp32. Здесь co-design «модель в кэше» становится реальным рычагом (×2.4 по β, **измерено**).
- На Kaggle T4 (таблица E, оценка): ~90–140M параметров на 1.8–2.9B токенов за 12–30 GPU-часов.
