# CDEMO_ADDENDUM_2 — R2-диагностика: дефект кодировки №2, переход к pairs-кодировке

**Дата: 2026-08-24 (тот же день, до прогонов R3). Родитель: CDEMO_PROTOCOL + ADDENDUM_1.**

## 1. Диагностика (дешёвая, вне протокольных плеч, 3 минуты)

После R2-smoke (оба плеча на случайном уровне по всем бакетам при 400 шагах) проведён
точечный тест: D2, только h∈{1,2}, 1500 шагов, B=64 — 96k сэмплов плотного надзора.
Результат: loss 3.466 ≈ ln(34)=3.526+слоты, acc(h=1)=0.089, acc(h=2)=0.023 — **случайный
уровень. Даже однократный lookup не встаёт.**

## 2. Причина (теперь не градиент, а геометрия кодировки)

Плоский список [π(1)..π(32)] заставляет модель адресовать ПОЗИЦИЮ j по ЗНАЧЕНИЮ x без
токена-ключа: нужен пик q(e_x)·k(pos_j + tok(π_j)) при j=x, т.е. выучить отображение
32 значений → 32 позиционных кода, игнорируя контент в ключах. На нашем бюджете это
не выучивается НИ ОДНИМ плечом (проверено на dense-2L — самом лёгком случае).

Вердикт: задача в плоской кодировке мертва для всех архитектур симметрично — это вторая
стендовая ошибка, а не результат об оси (той же логикой, что в ADDENDUM_1).

## 3. Фикс R3 (finальная revision; вторая по счёту, но обе — до каких-либо вердиктов PC)

Кодировка пар «ключ-значение»: **[1, π(1), 2, π(2), …, 32, π(32), SEP, x, BLK×20]**.
- Lookup становится стандартной induction-head копией (ключ по контенту id, значение —
  соседний токен) — известно как быстро выучиваемый 2-слойный контур.
- Цена честности ЗАФИКСИРОВАНА: токен-ось (CoT по слотам) становится доступной всем
  плечам в равной степени, поэтому сравнение FLOPs/параметров/оси-K — весь смысл демо.
- R=20 слотов: train h≤12, экстраполяция h∈[13,20] (8 бакетов), слоты 13..20 без надзора.
- T=86. Остальное (диета, lr, бюджет 4000 шагов, метрики, кил-критерии PC-1R..PC-7R)
  — без изменений; PC-4R-экстраполяция читается как h∈[13,20].

Прогоны R3 после этого аддиктума считаются первыми протокольными; результаты пишутся
в docs/CDEMO_RESULTS.md с явными вердиктами по букве PC-xR.
