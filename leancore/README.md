# LeanCore — дешёвое обучение и инференс языковых моделей: система, реализация, измерения

**Условие задачи:** на обычном железе (здесь: 2 ядра CPU, 3.8 ГБ RAM, без GPU, без внешних API,
без человека в петле) найти способ учить и использовать LM в разы/десятки раз дешевле
без потери качества; обдумать каждый компонент; доказать измерениями, не словами.

**Что здесь:** полный работающий конвейер (данные → тренировка → квантование → инференс),
A/B-измерения против честного baseline, отрицательный результат по одному из компонентов
(сообщён честно), и строгая граница между *измерено здесь*, *якорь из литературы* и *гипотеза*.

### Тренировка (3.03M параметров, 1000 шагов × 24×96 токенов, 2 ядра CPU)

| модель | FLOPs/ток (fwd, аналитика) | ток/с (общая скорость) | финальный val loss | примечание |
|---|---|---|---|---|
| baseline GPT (4 слоя, d=192) | 4 841 664 | 3196 | **5.0841** | эталон |
| **LeanCore ADR k=0.55** | **4 190 876 (−13.4%)** | **3666 (+14.7%)** | 5.0886 (+0.09%) | паритет качества |
| LeanCore ADR k=0.35 | 3 929 879 (−18.8%) | 4188 (+31.0%) | 5.1681 (+1.7%) | агрессивный режим |

**Изо-качественный анализ** (интерполяция по кривым val loss):
baseline достигает финального лосса LeanCore (5.0886) на шаге ~941, затратив 2.17М токенов и 681 с;
LeanCore — за 2.304М токенов и 628 с.
→ **обучение до того же качества: −8.1% FLOPs, −7.8% wall-clock** на этой конфигурации.
Кривые (см. `results/run_*.jsonl`): на протяжении средней части обучения lean стабильно
впереди по val loss при равном wall-clock; разрыв по токенам сокращается к концу —
маршрутизатор «дожимает» качество на финальном lr-спаде. Честный вывод: ADR даёт
однозначный, но **умеренный** выигрыш в цене обучения на этом масштабе; основной
потенциал связки — в других компонентах ниже.

### Вес и квантование (модель LeanCore k=0.55)

| состояние | val PPL | файл |
|---|---|---|
| fp32 | 159.7 | 18 276 108 B (state_dict, вкл. дуплет tied-эмбеддинга) |
| тернарные веса {−1,0,+1}×row-scale, zero-shot | 400.8 | |
| + QAT 500 шагов (~10 сек CPU-эквивалента времени тренировки) | **174.1** | **3 898 542 B (−78.7%, 4.7×)** |
| └ только матричные веса в бит-паке (2 бита/пар. с запасом над теор. 1.58) | | 0.83 МБ против 12.1 МБ fp32 → **14.6×**; теор. предел 1.58 бит → 20.4× |

Узкое место общего файла — эмбеддинги (fp16, 3.07 МБ). QAT-кривая (298→187→174 по шагам

1.58-бит квантование дороже всего даётся маленьким моделям; масштабный якорь литературы
(BitNet b1.58-линия, Ma et al. 2024 — из моей памяти, без верификации ссылок) показывает
закрытие зазора при обучении «квантованно с нуля» и при росте размера.

### Инференс (генерация, CPU, измерено)

| модель | tok/s |
|---|---|
| baseline fp32 | 145.7 |
| LeanCore fp32 | 155.0 (+6.4%) |
| LeanCore ternary | 38.7 (python-эмуляция квантования — см. честное примечание) |

Тернарный форвард здесь **не использует** int-ядра (их нет в этом рантайме) — пересчёт
квантования на каждый вызов. Реальный выигрыш тернарных весов — в памяти и пропускной
способности (генерация на CPU memory-bound: чтение весов — доминирующая стоимость;
−14.6× байт матриц на токен ⇒ проекция ускорения ~до того же порядка на bandwidth-bound
конфигурациях → **проекция, не измерение**).

- Дедупликация строк: удалено 21.8% дублей (31 285 из 143 675) — сделано; вклад в loss отдельно не мерил (корпус и так «чистый»), помечено как бесплатная гигиена.

## 1. Система: разбор каждого компонента и что с ним сделано

Принцип проекта: **дешевизна = мультипликативный стек**, а не один трюк. Компания-вендор уже
выжала dense-fp16-архитектуру; значит, выигрыш надо собирать по всем слоям стека сразу.
Ниже каждый компонент большой LLM и его LeanCore-аналог. Статусы: **[измерено]** — A/B на этом
железе; **[отрицат.]** — проверил, хуже; **[якорь]** — известный результат литературы
(по памяти, без ссылочной верификации); **[проекция]** — расчёт, требует проверки масштабом.

| # | Компонент LLM | Стандарт индустрии | LeanCore | Статус и цифры |
|---|---|---|---|---|
| 1 | Данные | сырые кравлы, фильтрация | дедуп (реализовано, −21.8% строк), авто-чистка разметки | [измерено частично] гигиена бесплатна, но не «размножает» данные |
| 2 | Токенизатор | BPE 100k+ | word-level 8k + <unk> (компактно для узкого домена) | [измерено] эмбеддинг 1.54M пар. вместо ~25M при 100k |
| 3 | Эмбеддинги | отдельная голова d×V | **weight tying** (голова=эмбеддинг) | [измерено] −1.54M параметров |
| 4 | Attention | полное O(T²) везде | causal SDPA; ключевая идея — считать его **только для важных токенов** (см. #6) | [измерено в связке] |
| 5 | FFN | dense SwiGLU 4× | считается только для маршрутизированных токенов | [измерено в связке] |
| 6 | **Компьют на токен** | каждый токен проходит все слои | **ADR** (Adaptive Depth Routing, вариация Mixture-of-Depths, Raposo et al. 2024 [якорь]): роутер «линейка d→1» выбирает top-k токенов на блок (k=0.55/0.35), остальные идут по residual-рукаву нулевой цены | [измерено] −13.4…−18.8% FLOPs/ток, −12.8…−23.7% время/токен при Δloss ≤ +0.09%…+1.7% |
| 7 | Веса при хранении/инференсе | fp16/bf16 | **тернарные {−1,0,+1}·s_row** (BitNet-1.58-стиль [якорь: Ma et al. 2024]), STE + короткий QAT | [измерено] матрицы 14.6× (20.4× теор.), весь файл 4.7× |
| 8 | Активации/KV-кэш | fp16 | короткий контекст + tying; окно [проекция для больших T] | здесь T=96, не горячая точка |
| 9 | Оптимизатор | Adam fp32 состояния | AdamW без изменений | оставлено как есть (8-бит состояния [якорь: 8-bit optimizers] — вне эксперимента) |
| 10 | Обучение | равномерный sampling | авто-куррикулум easy-first | [отрицат.] val хуже на 0.08 нита@300 шагов → выключено |

### Математика цены (сводная)

Для dense-модели: FLOPs_train ≈ 6·N·D (N — активные параметры, D — токены). LeanCore множители:
- ADR: FLOPs/ток по маршрутизированным блокам падает до ~ρ от dense (ρ=Σ-комбинация k-аппроксимаций; у нас измеренная цена шага −14.7% при k=0.55);
- качество за токен: кривые показывают, что ADR @ k=0.55 держит паритет вплоть до хвоста обучения; iso-loss цена обучения ↓ на ~8%.
- Инференс: цена генерации доминируется чтением весов ⇒ −14.6× байт матриц (тернар)
  транслируется в пропускную способность [проекция]; на GPU настоящий int2/int8-кернел дал бы
  и FLOPs-выигрыш [проекция по мотивам BitNet [якорь]].

**Стек-проекция до «Sonnet-уровня» (честная рамка, НЕ измерение):**
целевая планка качества лежит за пределами песочницы определённо. Корректная формулировка
результата: «набор техник, дающих измеренные множители на эталонной задаче» + протокол
фальсификации: повторить A/B на 30M/300M/3B, сверить power-law перенос множителей,
добавить int-кернелы. Заявлять «дотянул до Sonnet» по 3M-модели было бы враньём —
здесь показаны только множители и их порядки, с пометками.

## 2. Инженерная глава: как это вообще заработало на этом железе

В песочнице нет GPU-драйверов, а официальный PyTorch на PyPI — CUDA-сборка и падает на
импорте. Хабы датасетов/GitHub недоступны. Решено:
1. `pip install --no-deps torch` (PyPI) + ручное доустановление питон-зависимостей;
2. авто-генерация **ELF-стабов CUDA-библиотек с версионными символами** (gcc + version-script,
   40+ символов cupti/cudart/cublas/nvshmem/cufile), все функции возвращают код ошибки 100
   (не 0! — ноль=«успех» приводит к SIGSEGV в autograd, диагностировано и исправлено);
3. патч `_load_global_deps` в torch; итог: `torch 2.13.0` работает, `cuda.is_available()==False`,
   обучение устойчиво.
Это отдельная маленькая иллюстрация тезиса задачи: ограничения железа — повод для инженерии,
а не для отказа.

## 3. Файлы

- `prep_data.py` — чистка + дедуп + токенизатор (замеры: 1 075 956 токенов, OOV 3.52%)
- `model.py` — baseline GPT и LeanCore GPT (ADR-роутинг, tying, тернарные слои)
- `train.py` — тренер (AdamW, cosine, grad-clip, curriculum-опция, JSONL-логи)
- `quant.py` — конвертация в тернарные веса + QAT + бит-пакер (`results/lean_ternary.lc15`)
- `evalgen.py` — val PPL + генерация + замер tok/s
- `results/` — все сырые логи и отчёты (`run_*.jsonl`, `summary_*.json`, `quant_report.json`)

## 4. Воспроизведение

```bash
export LD_LIBRARY_PATH=/home/user/stublibs CUDA_VISIBLE_DEVICES=""
python3 prep_data.py
python3 train.py --variant baseline --tag base --steps 1000
python3 train.py --variant lean --tag lean --steps 1000 --kfrac 0.55
python3 quant.py --ckpt results/ckpt_lean.pt --qat_steps 500
python3 evalgen.py --ckpt results/ckpt_lean_ternary.pt --lean --ternary --prompt "the king"
```

## 5. Что предполагалось бы дальше (roadmap, не входит в измерения)

1. Полный перенос на int-ядра (тогда тернарные + ADR дадут множители и по инференс-времени);
2. ADR + MoE композиция (роутинг по глубине × по ширине ортогональны; [якорь] MoE=3–7×);
3. обучение «тернарно с нуля» вместо post-hoc QAT (по [якорю] BitNet зазор исчезает при масштабе);
4. генерация данных само-плейем от самой же модели (без API: bootstrap-цикл) — предмет
   отдельного эксперимента с фильтрами качества.

**Граница честности:** всё в §0 измерено здесь и сейчас; §1#7–9 и §5 помечены по источнику;
про Sonnet — только рамка и протокол. Никаких подставленных понятий: «дешевле» здесь =
меньше FLOPs/та же loss, меньше байт/та же loss — с числами.
